# 技术方案与架构

## 一、选型对比与结论

| 候选 | 优势 | 劣势 | 结论 |
|---|---|---|---|
| Python（mss + Pillow/TurboJPEG + asyncio，Tkinter/PySide，PyInstaller） | 开发快 | GIL 使采集/编码/多客户端发送互相竞争，高帧率困难；打包体积 100MB+、启动慢、反病毒误报率高 | 弃 |
| C++ / Qt | 性能上限最高 | 开发维护成本显著更高；本场景（教室、≤数十客户端、1080p/15FPS）用不到 | 弃 |
| Electron / Web | 跨平台 | 体积大、内存高、采集需额外原生层；本场景纯 Windows | 弃 |
| **C# / .NET 8 WinForms** | 原生性能无 GIL；GDI 采集与 JPEG 编码简单可靠；WinForms 界面开发成本低；`dotnet publish` 单文件发布，目标机零依赖 | 构建需 .NET 8 SDK（一次性）；self-contained 体积 ~60MB | **采用** |

**传输方案**：需求允许在"广播效果"与"组播实现"之间选择。选 **TCP 单播 + 每帧独立 JPEG（MJPEG 思路）**：
- TCP 保证有序可靠，JPEG 帧独立解码，丢帧不花屏——实现简单、鲁棒性好，适合教学场景的可靠性优先级。
- UDP/组播能省带宽但需要自定义可靠层（丢包重传、关键帧请求、组播路由兼容性），复杂度与"不过度设计"原则冲突；校园网对组播支持参差不齐。
- 带宽代价通过"画质/帧率取舍 + 慢客户端丢帧"控制，见下文限制说明。

**为什么不要求部署浏览器页面（服务端 HTTP 方案）**：需求明确"同一个软件包含两种模式"，且学生端需要姓名上报、连接状态、独立观看窗口；单 exe 双模式部署最简单。

## 二、协议设计（TCP，默认端口 9527）

每条消息：`1 字节类型 + 4 字节小端载荷长度 + 载荷`，载荷上限 8 MB。

| 类型 | 方向 | 载荷 | 说明 |
|---|---|---|---|
| ClientHello (0x01) | C→S | `[1字节协议版本][姓名UTF-8，≤60字节]` | 连接后第一句 |
| ServerWelcome (0x02) | S→C | 空 | 握手确认 |
| Frame (0x03) | S→C | JPEG 数据 | 屏幕帧 |
| Status (0x04) | S→C | `[1字节: 0=停止 1=直播中]` | 开始/停止共享通知 |
| Rejected (0x05) | S→C | 原因文本（UTF-8） | 版本不符等 |
| Ping (0x06) | C→S | 空 | 4 秒一次心跳 |
| SignInStart (0x07) | S→C | `[4字节小端: 剩余秒数]` | 签到发起时广播；中途连入的学生收到剩余时间 |
| SignInEnd (0x08) | S→C | 空 | 签到结束（到点或老师提前结束） |
| SignInSubmit (0x09) | C→S | `[1B学号长][学号][1B姓名长][姓名]` | 学生提交签到 |
| SignInResult (0x0A) | S→C | `[1字节: 0=成功 1=失败][原因]` | 服务端校验结果（学号唯一，一人一签） |

- **身份**：每个连接由服务端分配自增唯一 ID；显示层对同名做编号（张三、张三(2)），不依赖姓名区分连接。
- **停止共享不断开**：Status(0) 通知所有学生后连接保持，老师再次开始无需学生重连；关闭软件才断开。
- **保活**：两端启用 TCP keepalive（空闲 10s / 间隔 3s / 重试 3 次 ≈ 20s 内探测出"拔网线"式掉线）；学生端另有应用层心跳。

## 三、线程模型与关键机制

```
老师端                                  学生端
───────────────                        ───────────────
UI 线程（WinForms）                     UI 线程（WinForms）
  AcceptLoop（异步）                      ReceiveLoop（异步收消息）
  HandleClient ×N（每连接异步收）          DecodeLoop（后台解码 JPEG→Bitmap）
  SendLoop ×N（每学生专用发送线程）         PingLoop（心跳）
  CaptureEncode 线程（采集+编码）
```

- **一帧一次编码**：`CaptureEncodeLoop` 每帧 `CopyFromScreen` → JPEG 编码一次，得到只读 `byte[]`，把**同一份引用**投递给所有学生的队列，编码开销与学生数无关。
- **消息发送**：每个学生分别维护控制消息 FIFO（最多 32 条）和最新画面槽位（1 帧）。控制消息优先按顺序发送，画面到来时替换旧帧，避免停止共享或签到通知被画面挤掉。控制消息积压超过上限、或同步 `Write` 超过 15 秒时断开该学生。每学生使用专用发送线程，避免阻塞线程池。
- **学生端实时显示**：解码队列最多保留 2 帧，满时丢旧帧；观看窗口只保留最新待显示位图，并最多安排一次 UI 更新，替换的位图及时释放。
- **输入限额**：消息头长度校验（≤8MB）、姓名 ≤60 字节、握手超时 10 秒、连接数上限 100。
- **帧率控制**：采集线程每帧读取 `TargetFps` 字段并按"处理耗时 + Sleep"定速，UI 改帧率立即生效。**"编码 X FPS"每秒实测上报**，达不到目标值时如实显示。
- **采集**：GDI `CopyFromScreen` 抓整个虚拟桌面（多显示器拼合，进程 PerMonitorV2 取物理像素），随后按指针热点和虚拟桌面坐标叠加老师的鼠标指针。优点是零依赖、兼容性最好；抓不到部分硬件保护内容（如部分 DRM 视频画面），对教学场景无影响。
- **DPI**：csproj 设 `ApplicationHighDpiMode=PerMonitorV2`，保证高缩放屏（125%/150%）下采集到物理分辨率、文字清晰。
- **UI 不阻塞**：采集/编码/网络/解码全部后台线程；事件经 `BeginInvoke` 回 UI。
- **签到保存**：每轮使用独立 JSON 文件，保存在 `%LOCALAPPDATA%\教室屏幕共享\签到记录`。提交成功前先保存更新后的名单，采用临时文件加原子替换；保存失败不会计入人数或返回成功，可修复目录后重试。新一轮保留之前的文件。

## 四、打包

- `scripts/publish.ps1` 产出两种形态：
  - **免安装版**（self-contained，EXE 约 59.7 MB）：`-p:PublishSingleFile=true -p:EnableCompressionInSingleFile=true`；不需要预装运行时。发布目录还包含运行时原生 DLL，应整体复制或压缩后分发。
  - **需运行时版**（实测 0.2 MB）：目标电脑需装 [.NET 8 Desktop Runtime x64](https://dotnet.microsoft.com/download/dotnet/8.0)。
- WinForms 不支持 IL 裁剪（trimming），故 self-contained 体积较大，属已知权衡；对 U 盘拷贝分发无碍。
- 无外部 NuGet 包依赖；免安装发布目录中的运行时 DLL 由 .NET 发布工具生成。本项目源码采用 MIT 许可证，见根目录 `LICENSE`。
- `bin/`、`obj/`、`publish/` 不进入代码仓库；可运行程序包单独作为发行版附件上传。

## 五、已知性能限制（实测数据见《测试报告》）

1. **编码上限**：GDI+ JPEG 编码 1440×900 实测约 20–25ms/帧，理论单客户端 40–51 FPS；60 FPS 目标在多数教室机上达不到，UI 会如实显示实际值。
2. **带宽线性增长**：单播下每个学生一份流量（111KB/帧 × 帧率 × 人数）。30 人 × 15FPS ≈ 390 Mbps，需要千兆网络；百兆网络建议 5–10 FPS 或减少人数。
3. **多屏**：共享整个虚拟桌面（所有显示器拼合），分辨率变大时帧更大、编码更慢。
4. **画质固定** JPEG 质量 70：未提供画质调节（未在需求内）。
5. **无 GPU 加速**：GDI 采集 + CPU 编码；引入 Windows Graphics Capture + 硬件 H.264 可大幅提升上限，作为后续改进方向（见下）。

## 六、后续改进建议（本次未实现）

- H.264/HEVC 硬件编码（MediaFoundation / Windows Graphics Capture）+ WebRTC 或自研 RTP：带宽可降一个数量级，60 FPS 可达；代价是实现复杂度和打包 native 依赖。
- 差量/区域编码：静止画面跳帧或只编码变化区域，进一步降 CPU 与带宽。
- 服务端按学生能力自适应画质（慢客户端降分辨率）。
- IPv6 支持、可选指定单显示器共享。
